## 🔴 Критичные

### 1. Любой залогиненный пользователь видит и скачивает чужие файлы

- `/static/*` отдаётся через `http.FileServer(http.Dir("data"))`
  ([router.go:160-161](backend/cmd/api/router.go#L160)).
- `http.FileServer` показывает содержимое каталогов. `GET /static/files/`,
  `/static/users/` и `/static/thumbnails/` возвращают список всех файлов всех
  пользователей.
- Проверки владельца нет, поэтому по этому списку можно скачать любой
  конспект, PDF или аватар.

**Исправление:** отключить листинг каталогов и отдавать файлы через хендлер,
который проверяет владельца (или хотя бы использует неугадываемые пути без
листинга).

### 2. Нет ограничения частоты запросов

Ни один маршрут не защищён rate limit:

- `POST /api/auth/login`: перебор паролей без ограничений.
- `POST /api/auth/login/totp`: перебор 6-значного кода (подробнее в
  DATABASE_REVIEW.md, пункт 8).
- `POST /api/auth/reset-password/request` и `POST /api/auth/confirm/resend`:
  можно засыпать любой адрес письмами.
- `POST /api/auth/register`: массовое создание аккаунтов.

**Исправление:** rate limit по IP и по email/user ID, например через
`go-chi/httprate`.

### 3. Загрузка изображений уязвима к «бомбе распаковки»

- `SaveImageAsWebp` ([media/service.go:19](backend/internal/media/service.go#L19))
  сначала полностью декодирует картинку через `image.Decode` и только потом
  проверяет размеры.
- PNG размером меньше 2 МБ может заявить разрешение 50000×50000. Декодер
  попробует выделить гигабайты памяти, и процесс упадёт по OOM.

**Исправление:** сначала `image.DecodeConfig`, проверить ширину и высоту, потом
декодировать.

### 4. Нет ограничений на размер тела запроса

- JSON-хендлеры читают тело без `http.MaxBytesReader`, так что можно прислать
  JSON любого размера.
- `UploadFile` ([subject/handler.go:447-468](backend/internal/subject/handler.go#L447))
  вызывает `r.FormFile` без общего лимита: multipart-парсер пишет всё, что не
  влезло в 32 МБ памяти, во временные файлы. Лимит в 50 МБ проверяется уже после
  этого.
- В этом же хендлере файл сохраняется на диск раньше, чем проверяются ID
  пользователя и ID предмета.

### 5. HTTP-сервер без таймаутов и плавной остановки

- `http.ListenAndServe` ([app.go:166](backend/cmd/api/app.go#L166)) использует
  сервер без `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout` и `IdleTimeout`.
  Медленные клиенты (Slowloris) держат соединения бесконечно.
- Нет обработки SIGTERM: при остановке контейнера запросы обрываются, а
  `defer app.close()` не выполняется.

## 🟠 Высокие

### 6. Длинный пароль на кириллице даёт 500

- Валидация ограничивает пароль 72 символами (`utf8.RuneCountInString`,
  [validation.go:67](backend/internal/auth/credentials/validation.go#L67)).
- bcrypt ограничен 72 байтами, и `x/crypto` v0.53 возвращает
  `ErrPasswordTooLong`. Кириллический пароль из 37+ символов проходит валидацию
  и падает при хешировании с 500.

**Исправление:** считать длину в байтах (`len(password) > 72`).

### 7. Секретные токены попадают в логи

- `X-Correlation-ID` берётся из заголовка клиента без проверки
  ([logger.go:36](backend/internal/middlewares/logger.go#L36)), так что клиент
  может подсунуть в логи произвольную строку любой длины.

### 8. Важные действия выполняются без повторной проверки пароля

С одной украденной cookie можно:

- сменить email (`PATCH /api/users/me/email`), а затем сбросить пароль через
  новую почту, то есть полностью захватить аккаунт;
- отключить TOTP (`DELETE /api/auth/totp`);
- перенастроить TOTP (DATABASE_REVIEW.md, пункт 2).

**Исправление:** требовать текущий пароль или TOTP-код для этих действий.

### 9. Подтверждение email ни на что не влияет

- `is_email_verified` нигде не проверяется: неподтверждённый пользователь
  пользуется всем API.
- `POST /api/auth/confirm/{token}` требует, чтобы пользователь был залогинен.
  Если ссылку открыть на другом устройстве, подтвердить почту не получится.

### 10. Можно узнать, зарегистрирован ли email

- Логин отвечает быстрее, если пользователя нет: bcrypt не вызывается.
- Регистрация отвечает 409 на занятый email. Это обычно приемлемо, но вместе с
  разницей во времени ответа при логине перебор адресов остаётся возможным.
  (Эндпоинт `/api/auth/reset-password/request` уже исправлен и всегда возвращает 204 No Content).

### 11. Входные данные почти не проверяются

- Задачи: хендлер не проверяет ни одного поля. Нет проверок `name`, enum-полей и
  длины `description`, ошибки доходят до БД и превращаются в 500.
- Предметы: нет ограничений длины `name`. `note` длиннее 200 символов падает
  в БД с 500.
- Неизвестные поля JSON молча игнорируются (`DisallowUnknownFields` не
  используется), поэтому опечатка в имени поля не даёт ошибки.
  (Смена email уже валидируется через `mail.ParseAddress`, проверку на пустоту и неизменность).

### 12. Почта отправляется синхронно и без защиты

- Письмо отправляется прямо в обработчике запроса. Если SMTP недоступен или
  отвечает медленно, регистрация, смена email и сброс пароля висят и падают
  с 500, хотя изменения в БД уже сделаны.
- `smtp.Dial` вызывается без таймаута и без TLS/STARTTLS.
- `SMTP_USERNAME`, `SMTP_PASSWORD`, `MAIL_PROVIDER` и `MAIL_FROM` из
  docker-compose игнорируются. Отправитель захардкожен как
  `noreply@studify.com`, а в compose указан `noreply@studify.dev`.
- В письмах нет заголовков `Date` и `Message-ID`, поэтому настоящие почтовые
  серверы, скорее всего, будут отправлять их в спам.

## 🟡 Средние

### 13. Ответы с ошибками несогласованы

- Ошибки отдаются простым текстом, а успешные ответы — JSON. Клиенту приходится
  разбирать оба формата.
- Внутренние сообщения уходят клиенту: `failed to read data: <ошибка парсера>`.
- Сообщение о дубле предмета на русском («Предмет с таким названием уже
  существует»), все остальные на английском.
- Отсутствие user ID в контексте в одних хендлерах даёт 401, в других 500.
- Ошибки загрузки файла (неверный тип, больше 50 МБ) возвращаются как 500
  вместо 415 и 413.

### 14. Конфиг и окружение

- Длина JWT-секретов не проверяется: секрет `a` пройдёт.
- Продакшн определяется по-разному: cookies считают продом `prod` и
  `production`, а логгер — только `prod`
  ([app.go:192](backend/cmd/api/app.go#L192)).
- В проде логгер работает на уровне `Debug`, в разработке — на `Info`. Похоже,
  уровни перепутаны.

### 15. Бизнес-логика в хендлерах, код трудно тестируется

- В пакетах `subject`, `task` и `dashboard` хендлеры по-прежнему ходят в БД напрямую.
  (Для `auth`, `user`, `mfa`, `rc`, `resetpassword`, `emailconfirm` и `token` сервисный
  слой и интерфейсы уже выделены).

### 16. Дублирование кода

- Загрузка аватара и миниатюры — копии друг друга.
- JSON пишется тремя способами: `writeJSON` в subject, ручной `json.NewEncoder`
  в остальных хендлерах, разная обработка ошибок кодирования.
- ID из URL разбирается то через `httpx.GetID`, то вручную через
  `strconv.ParseInt`.
- Две почти одинаковые обёртки `ResponseWriter` в middlewares для логов и
  метрик.

### 17. CSRF держится только на `SameSite=Lax`

Отдельной CSRF-защиты нет. Для текущих маршрутов этого в целом хватает, но
защита пропадёт, если фронт и API окажутся на разных поддоменах одного сайта
или появится изменяющий GET-запрос.

## 🟢 Низкие

### 18. Мёртвый код и заготовки

- `VerifyTOTP` ([mfa/handler.go:112](backend/internal/auth/mfa/handler.go#L112))
  не подключён к роутеру.
- `UserRequest` содержит лишние поля `IsEmailVerified` и `TOTPCode // temp!`.
- В коде остались закомментированные маршруты и TODO («fix, rename .etc»).

### 19. Именование и стиль

- Пакет `rc` импортируется под коротким алиасом.
- Опечатки: `enabld`, `recieve`.
- Комментарии на русском и английском вперемешку.

### 20. JWT

- Access-токен разбирается без `WithExpirationRequired`, в отличие от
  refresh-токена. Сейчас сервер всегда ставит `exp`, но проверка должна быть
  симметричной.
- Нет `audience`. Access-токен остаётся действительным до 15 минут после
  выхода. Для такой схемы это нормально, но стоит держать в голове.

### 21. Docker и сборка

- В `Dockerfile.dev` версия `air@latest` не закреплена, поэтому сборка может
  сломаться при выходе новой версии.
- Контейнер работает от root.
- Продакшн-Dockerfile нет, есть только dev-вариант с hot reload.

### 22. HTTP-примеры в `backend/postman/` устарели

- `POST /api/auth/totp` не существует.
- Нет примеров для TOTP, сброса пароля, подтверждения email, профиля и
  загрузки файлов.
- В примерах похожий на настоящий адрес `maxonchik@gmail.com`. Лучше
  использовать `example.com`.

### 23. Метрики

`/metrics` открыт без авторизации. В Docker это не страшно, но при публикации
API наружу его нужно закрыть.

3. Пункты 13–17: единый формат ошибок, сервисный слой для оставшихся модулей (subject, task), новые тесты.
