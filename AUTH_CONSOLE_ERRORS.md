# Ошибки 401 в консоли для неавторизованного пользователя

Дата: 2026-10-04.

Красные строки про 401 в консоли браузера из кода не скрыть: браузер сам печатает
их для любого ответа не из диапазона 2xx. Убрать их можно только одним способом —
сделать так, чтобы в обычной ситуации «пользователь не залогинен» сервер не
отвечал ошибкой.

## Откуда сейчас берутся ошибки

Для гостя каждая загрузка страницы проходит так:

1. `GET /api/users/me` → 401: access-cookie нет.
2. `frontend/src/shared/api/http/request.ts` видит 401 и пробует обновить сессию:
   `POST /api/auth/refresh` → тоже 401.
3. `getMe` (`frontend/src/entities/user/api/get-me.ts`) ловит ошибку и
   возвращает `null`.

Получается две красные строки на каждый заход, хотя ничего не сломалось.

## Решение (рекомендую): эндпоинт проверки сессии

Добавить на бэкенде `GET /api/auth/session` без middleware `ValidateAuth`. Он
всегда отвечает 200:

| Состояние | Ответ |
| --- | --- |
| Нет cookies | `{ "authenticated": false }` |
| Access-токен валиден | `{ "authenticated": true, "user": {...} }` |
| Access истёк, refresh валиден | Обновляет cookies (та же логика, что в `RefreshTokens`) и возвращает пользователя |
| Refresh тоже невалиден | Очищает cookies и отвечает `{ "authenticated": false }` |

На фронте `userQuery` вызывает `/api/auth/session` вместо `/api/users/me`.
Тогда:

- гость не получает ни одного 4xx, и консоль чистая;
- `getMe` больше не глушит все ошибки подряд: 500 и сетевые ошибки честно
  пробрасываются (пункт 4 в [FRONTEND_REVIEW.md](FRONTEND_REVIEW.md));
- 401 остаётся только там, где он действительно означает проблему: сессия
  истекла посреди работы.

Заодно в `request.ts` стоит запретить автоматический refresh для
`/api/auth/*`, иначе неверный пароль при логине тоже запускает обновление сессии
(пункт 3 в FRONTEND_REVIEW.md).

## Альтернатива попроще: cookie-флаг

Бэкенд при логине и refresh ставит рядом с HttpOnly-токенами обычную cookie без
секрета, например `has_session=1`, и удаляет её при выходе. Фронт читает её
через `document.cookie`:

- флага нет → сразу считаем пользователя гостем, запрос не делаем;
- флаг есть → вызываем `/api/users/me` как сейчас.

Это быстрее сделать, но если флаг и реальные cookies разойдутся (например,
refresh-токен истёк через 30 дней), одна красная строка всё равно появится.
Первый вариант надёжнее.

## Логи бэкенда

Там это тоже стоит поправить, отдельно от консоли браузера:

- в `RefreshTokens` (`backend/internal/auth/handler.go`) ошибки разбора и
  проверки токена (просрочен, отозван, не найден) пишутся через `slog.Error`.
  Для ожидаемых ситуаций нужен `slog.Info` или `slog.Warn`, а `Error` оставить
  только для сбоев БД;
- в `RequestLogger` (`backend/internal/middlewares/logger.go`) выбирать уровень
  по статусу: 2xx и 3xx — `Info`, 4xx — `Warn` (или `Info` для 401), 5xx —
  `Error`. Тогда по уровню `Error` видны только настоящие проблемы.

## Только для себя, временно

В DevTools Chrome можно включить «Hide network» в настройках консоли
(шестерёнка), и сетевые ошибки перестанут выводиться. Но это скрывает и
настоящие ошибки, поэтому как постоянное решение не годится.
