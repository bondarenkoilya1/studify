# Backend Auth Problems

Документ фиксирует известные проблемы текущей реализации авторизации. Это не
описание желаемого поведения, а список рисков, которые ещё требуется исправить.

## 1. Пользовательские endpoints дают слишком широкие права

Маршруты `/api/users` доступны любому авторизованному пользователю и работают
по `username` из URL, а не по identity текущей сессии. Пользователь может
изменять и удалять чужие аккаунты или удалить всех пользователей.

Self-service API профиля и административный API должны быть разделены. Пока нет
ролей и проверки admin-прав, глобальный CRUD пользователей нельзя безопасно
публиковать.

## 2. Logout не отзывает refresh token в браузере

Refresh cookie создаётся с `Path=/refresh`, тогда как logout расположен по
адресу `/api/auth/logout`. Браузер не отправляет эту cookie на logout, поэтому
backend очищает cookies, но обычно не отзывает refresh token в базе.

Logout должен завершать серверную сессию, а не только очищать состояние
браузера.

## 3. Refresh endpoint не получает refresh cookie

Refresh cookie имеет `Path=/refresh`, но endpoint расположен по адресу
`/api/auth/refresh`. В обычном браузерном сценарии cookie не будет приложена к
запросу, поэтому rotation фактически не работает.

Путь cookie необходимо согласовать с реальными refresh и logout routes.

## 4. Смена пароля не инвалидирует существующие сессии

После изменения пароля старые refresh tokens остаются активными. Если пароль
меняется из-за компрометации, уже украденная сессия продолжает работать.

Смена пароля должна отзывать активные refresh tokens пользователя либо
увеличивать версию сессии, проверяемую при обновлении токенов.

## 5. Register/login могут оставить частично авторизованное состояние

Access cookie выставляется до успешной записи refresh token в базу. Если
создание refresh token завершается ошибкой, клиент получает `500`, но в ответе
уже может присутствовать рабочий access token.

Выдача сессии должна быть атомарной на уровне бизнес-поведения: ошибка не должна
оставлять клиенту частично созданную сессию.

## 6. Нет защиты от перебора паролей

Login endpoint не использует rate limiting, throttling, backoff или временную
блокировку. Это оставляет возможность online brute force и credential stuffing,
а также создаёт поверхность для избыточной нагрузки на bcrypt и сервер.

Ограничение должно учитывать как источник запросов, так и целевой аккаунт.

## 7. Refresh rotation не имеет полноценного reuse detection

В схеме есть `replaced_by_token_id`, но lineage токенов не используется как
часть модели ротации. Повторное применение старого refresh token не приводит к
отзыву всей token family и не сохраняет полноценный сигнал компрометации.

Нужно связать старый и новый токены, детектировать повторное использование и
отзывать соответствующую цепочку сессии.

## 8. Возможна гонка при одновременном refresh

Проверка refresh token и его отзыв разделены по времени. Два параллельных
запроса с одним токеном могут оба пройти проверку до фиксации отзыва и создать
несколько новых refresh tokens.

Rotation должна выполняться транзакционно с блокировкой строки или условным
атомарным update, гарантирующим одноразовое использование токена.

## 9. JWT secrets проверяются только на непустоту

Конфигурация не проверяет длину, случайность и различие access/refresh secrets.
Слабые или одинаковые secrets могут попасть в production без fail-fast ошибки.

Production-конфигурация должна требовать независимые secrets достаточной
энтропии.

## 10. Cookie auth не имеет явной CSRF-модели

Авторизация основана на cookies, которые браузер прикладывает автоматически.
`SameSite=Lax` снижает часть риска, но не заменяет сформулированную CSRF-модель
для state-changing запросов.

До публичного запуска необходимо определить допустимые origins и внедрить
проверяемую CSRF-защиту либо другое обоснованное ограничение запросов.
